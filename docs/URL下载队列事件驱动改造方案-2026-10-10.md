# URL 下载队列：轮询改事件驱动 + 优先级方案

> 文档日期：2026-10-10
> 涉及模块：`server/internal/file/url_dispatcher.go`、`server/internal/repositories/url_download_task_repo.go`、`server/internal/models/url_download_task.go`、`server/main.go`

---

## 1. 背景与问题

URL 上传（下载）任务由后台队列调度器 `URLDownloadDispatcher` 处理。调度循环 `run()` 当前使用 **1 秒固定 ticker** 作为触发源之一：

```go
func (d *URLDownloadDispatcher) run() {
	ticker := time.NewTicker(time.Second)
	defer ticker.Stop()
	d.dispatch()
	for {
		select {
		case <-d.stop:
			return
		case <-d.notify:
			d.dispatch()
		case <-ticker.C:      // ← 兜底轮询
			d.dispatch()
		}
	}
}
```

每次 `dispatch()` 都会调用 `ClaimNextPending()`，其内部使用 `First()` 取任务。队列为空时 GORM 默认 logger 会打印 `record not found`，于是**空队列时日志以每秒一条的频率刷屏**：

```
2026/10/10 10:15:52 url_download_task_repo.go:221 record not found
[0.492ms] [rows:0] SELECT * FROM `url_download_tasks` WHERE status = "pending" AND queued_at <= "..." ORDER BY ... LIMIT 1
```

这不是故障，而是「1 秒兜底轮询 + GORM 默认记录 NotFound」叠加的噪音。

## 2. 现状分析

### 2.1 轮询到底在兜什么

`notify` 通道是事件驱动的主力（新任务入队、槽位释放都会 `Notify()`），ticker 只在兜两件**没有事件可依赖**的事：

1. **重试退避到期**：自动重试任务由 `RequeueForRetry(id, retryBackoff(n))` 重新入队，`queued_at = now + 退避`（30s × n，上限 5 分钟）。入队时虽然调了 `Notify()`，但此刻任务尚未到期、领不到；此后**再没有任何事件**会在它到期时唤醒调度器。
2. **调大并行上限**：配置热更新后 `MaxConcurrent` 变大，但没有事件通知调度器。

### 2.2 现有事件源清单

| 事件 | 触发点 | 现状 |
|---|---|---|
| 新任务入队 | `url_task_handlers.go` | ✅ `Notify()` |
| 手动重试 | `url_task_handlers.go` | ✅ `Notify()` |
| 自动重试入队 | `url_download.go` | ✅ `Notify()` |
| 槽位释放（任务结束） | `url_dispatcher.go` | ✅ `Notify()` |
| 启动对账唤醒 | `main.go` | ✅ `Notify()` |
| admin 重试 | `main.go`（`SetTaskHooks`） | ✅ `Notify()` |
| **配置保存（并发上限变化）** | — | ❌ 缺失 |
| **退避到期** | — | ❌ 缺失（靠 ticker 兜） |

### 2.3 调度器生命周期

`URLDownloadDispatcher` 是**独立常驻 goroutine**，在 `main.go` 中 `urlDispatcher.Start()`（内部 `go d.run()`）启动一次：

- 不属于 `runCtx.run()` 里通过 `workerStart` 注册的那批 worker（http/ftp/cleanup/index-scan/…），**不随配置热重启重建**。
- 每次调度用 `currentLimit()` 直接读配置热值，所以并发上限变更能生效——但也正因「配置变更」本身不产生事件，才需要 ticker 兜底。

### 2.4 排序与优先级

`ClaimNextPending()` 排序为 `queued_at ASC, created_at ASC`，**纯时间序、无类别优先级**。重试任务因 `queued_at` 被退避推后，能排到「当时已入队」任务的后面；但之后到达、`queued_at` 更早的新任务仍可能插到它前面——优先级完全由时间决定，并非「新任务永远优先」。

## 3. 方案

### 3.1 目标

- 删除 1 秒 ticker，改为**事件驱动 + 按需精确唤醒**。
- 引入**类别优先级**：新任务 / 手动重试 > 自动重试。
- 退避延迟继续由 `queued_at` 承载，**不**引入「取出后 sleep」。

### 3.2 调度循环改造

删除 ticker，改为单个可重置的 `*time.Timer`（仅在 `run` 协程内操作）：

```go
func (d *URLDownloadDispatcher) run() {
	d.dispatch() // 启动即调度一轮
	for {
		select {
		case <-d.stop:
			return
		case <-d.notify:
			d.dispatch()
		case <-d.timer.C: // 退避到期唤醒
			d.dispatch()
		}
	}
}
```

`dispatch()` 保持「领满额度」的骨架，末尾增加收尾：

```go
func (d *URLDownloadDispatcher) dispatch() {
	limit := int32(d.currentLimit())
	for atomic.LoadInt32(&d.inFlight) < limit {
		task, err := d.repo.ClaimNextPending() // 只领 due，且按优先级排序
		if err != nil { /* 记录并 return */ }
		if task == nil { break }
		atomic.AddInt32(&d.inFlight, 1)
		go func(t *models.URLDownloadTask) {
			defer func() { atomic.AddInt32(&d.inFlight, -1); d.Notify() }()
			d.handler.executeURLDownloadTask(t)
		}(task)
	}
	d.armTimer() // 决定下一次唤醒
}
```

`armTimer()` 区分「取不出」的两种情况：

- **`inFlight >= limit`**：是「槽位满」停的 → 不 arm（槽位释放会 `Notify`）。
- **否则是「取不出」停的** → 查询最早的 pending 任务 `queued_at`：
  - 有且 `dueAt > now`：`timer.Reset(dueAt - now)`（clamp 最小 100ms，防忙转）。
  - 有但 `dueAt <= now`（竞态）：`timer.Reset(minDelay)`，马上再领一次。
  - 无 pending：`timer.Stop()`，真正等待事件。

> Reset 采用标准 stop+drain 写法（`if !timer.Stop() { select { case <-timer.C: default: } }` 再 `Reset`）。因 `timer.C` 与 `Reset` 都在 `run` 协程内，无并发问题。

> 变体：也可用 `time.AfterFunc(delay, d.Notify)`，但进程重启后定时器全部丢失、需额外对账；`select + timer` 更自洽，故选它。

**关键认知**：「取不出」≠「没有任务」。退避中的任务（`queued_at` 在未来）属于「有任务但未到期」，若按「停止等事件」处理，将永远等不到事件——这正是 ticker 在偷偷兜的坑。

### 3.3 优先级策略

- 新增 `priority int` 列（AutoMigrate 自动加列）：
  - 新任务 `Create` → `0`
  - 手动重试 `ResetToPending` → `0`（高）
  - 自动重试 `RequeueForRetry` → `1`（低）
- `ClaimNextPending` 排序改为 `priority ASC, queued_at ASC, created_at ASC`。
- 建议把复合索引由 `(status, queued_at)` 扩展为 `(status, priority, queued_at)`（队列量可控，非必须）。

> 免迁移替代：不新增列，改用 `ORDER BY (retry_count = 0) DESC, queued_at ASC, created_at ASC`（手动重试已把 `retry_count` 清零，语义刚好吻合）。显式列更清晰，推荐显式列。

### 3.4 启动对账

`RequeueInterrupted` **保持不变**：

- `downloading` → `pending`，**不动 `queued_at`**（保留现行为），重启后立即被领取。
- `pending` 里的退避任务**不重置**：启动首轮 `dispatch()` 的 `armTimer()` 会算出最近到期时刻并接管，无需额外对账。
- `pending` 记录本身**不需要重置状态**。

### 3.5 日志噪音修复

根因：`ClaimNextPending` 使用 `First()`，无记录时 GORM 默认 logger 打印 `record not found`。

- **推荐**：该方法改用 `Find` + `Limit(1)`，从源头不产生 `ErrRecordNotFound`（精准，不影响全局日志行为）。
- 备选：GORM logger 配 `IgnoreRecordNotFoundError: true`（全局静默，影响面大，慎用）。

## 5. 边界与风险

- **重试饥饿**：严格「重试永远低一级」在持续新任务涌入时会压低重试。已确认**接受**：URL 下载任务数量可控，且自动重试次数有上限（默认 3），不会无限堆积。
- **时钟**：退避计算统一用 `utils.Now()`（UTC）同源，勿混本地时区。日志中 `10:15` 对 `02:15` 的 8 小时差只是「日志格式化用本地时间、存储用 UTC」，逻辑一致，非缺陷。
- **历史数据**：迁移时 `priority` 默认 0，存量退避任务会变高优先级，但 `queued_at` 在未来仍受退避约束；如需精确，可在迁移时把 `retry_count > 0` 的记录置 1。
- **钩子重复**：调度器常驻、不随热重启重建，配置保存钩子只在 `main.go` 注册一次，无重复注册问题。

## 6. 验证

- **单测**：
  - `ClaimNextPending` 的优先级排序（新任务先于自动重试）。
  - `armTimer` 三分支：有未来到期 / 有到期 / 空队列。
- **手测**：
  - 空队列时日志不再每秒刷 `record not found`。
  - 新任务立即执行；失败任务退避到期后自动重试。
  - 后台调大并发上限后立即生效（不再等 1 秒）。

## 7. 决策记录

| 决策点 | 结论 |
|---|---|
| 触发机制 | 删除 1 秒 ticker，改事件驱动 + 按需 arm timer |
| 退避到期处理 | 调度器取空后按最近到期时刻 arm 一次性 timer（非 `AfterFunc`） |
| 退避表达 | 继续用 `queued_at`，不引入「取出后 sleep」 |
| 启动时 pending 重置 | 不重置；`downloading` 照旧重置为 `pending` |
| 手动重试优先级 | 高（`priority = 0`，等同新任务） |
| 重试饥饿 | 接受 |
| 日志噪音 | `ClaimNextPending` 改 `Find/Limit(1)` |
