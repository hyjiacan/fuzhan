# 数据库交互审查报告

> 审查日期: 2026-09-29
> 审查范围: `server/` 全量 Go 代码（业务代码，不含 `third_party/` 与测试初始化）
> 审查依据: 新增规范《数据库交互规范》（[开发指南](./development-guide.md#数据库交互规范) / [架构文档](./architecture.md#数据库访问规范)）
> 目标数据库: SQLite / MySQL / PostgreSQL

---

## 一、审查依据（本次新增的规范条款）

项目此前**没有**任何文档明确规定"数据库交互必须使用 ORM、特殊情况必须兼容多数据库"。本次已在两处补充：

| 文档 | 位置 | 内容 |
|------|------|------|
| `docs/development-guide.md` | `## 代码规范` → `### 数据库交互规范` | 编码细则：ORM 优先、原生 SQL 准入条件、表名/标识符规则 |
| `docs/architecture.md` | 新增 `## 数据库访问规范` | 设计层面强制约束，含引擎专有语法禁区清单 |

规范核心要求：

1. **一律通过 ORM（GORM）完成**数据库读写；表结构/索引由模型定义 + `AutoMigrate` / `db.Migrator()` 管理。
2. **确需原生 SQL 时**（复杂聚合、批量更新等特殊情况），必须同时满足：
   - 兼容 SQLite / MySQL / PostgreSQL，不得使用任一引擎专有语法/函数/类型；
   - 值参数化绑定（`?`），禁止拼接用户输入；
   - 表名取自模型 `TableName()`，列名/排序字段来自白名单。

## 二、结论摘要

| 严重级别 | 问题类别 | 命中数量 | 影响 |
|----------|----------|----------|------|
| 🔴 高 | MySQL 下语法错误或结果错误 | 5 组 | MySQL 部署下相关功能失效或数据错误 |
| 🟠 中 | PostgreSQL 下语法错误（反引号标识符） | 16 处调用点 | PostgreSQL 部署下相关接口报错 |
| 🟡 中 | 手写 DDL 绕过 Migrator | 2 处 | 索引创建不可靠、跨库失败被静默吞掉 |
| 🔵 低 | 硬编码表名（规范违反，功能正常） | 14 处 | 表名变更/多库适配时易失效 |
| ⚪ 说明 | 原生 SQL 但参数化且跨库兼容（可接受的特殊情况） | 12 处 | 建议补注释，不阻断 |

**总体判断**：绝大多数业务查询（仓储层、服务层）都规范地使用了 GORM，未发现 SQL 注入类问题（值均已参数化）。**核心风险不在注入，而在"方言兼容"**——多处原生 SQL 与反引号标识符在 MySQL / PostgreSQL 上会直接报错或产生错误结果。默认 SQLite 部署下这些代码可正常运行，因此问题被长期掩盖。

## 三、🔴 高危问题（MySQL 下报错或结果错误）

### 3.1 `ApplyExistingFileFilter` —— `||` 与两参数 `TRIM`

**文件**：`server/internal/repositories/upload_repo.go:30-55`

```go
func ApplyExistingFileFilter(q *gorm.DB) *gorm.DB {
	return q.Where(`(
		operation_records.action = 'search'
		OR operation_records.upload_type NOT IN ('regular', '')
		OR (operation_records.file_record_id > 0 AND EXISTS (
			SELECT 1 FROM file_records_public frp
			WHERE frp.id = operation_records.file_record_id
			  AND frp.status = 'active'
			  AND frp.deleted_at IS NULL
		))
		OR (operation_records.file_record_id = 0 AND EXISTS (
			SELECT 1 FROM file_records_public frp
			WHERE frp.status = 'active'
			  AND frp.deleted_at IS NULL
			  AND frp.root_name = operation_records.root_name
			  AND (
				(operation_records.full_path IS NOT NULL AND operation_records.full_path != ''
					AND (frp.full_path = operation_records.full_path
						 OR frp.full_path = ('/' || operation_records.full_path)))   -- ← 第 48 行
				OR (operation_records.full_path IS NULL OR operation_records.full_path = ''
					AND frp.file_name = operation_records.file_name
					AND TRIM(frp.file_path, '/') = TRIM(operation_records.file_path, '/'))  -- ← 第 51 行
			  )
		))
	)`)
}
```

| 问题 | 方言事实 | 后果 |
|------|----------|------|
| 第 48 行 `'/' \|\| operation_records.full_path` | MySQL 默认将 `\|\|` 解析为**逻辑 OR**，而非字符串拼接 | 表达式退化为布尔值，匹配结果错误（SQLite/PostgreSQL 正常） |
| 第 51 行 `TRIM(frp.file_path, '/')` | MySQL **不支持**两参数 `TRIM(str, chars)`（仅支持 `TRIM(str)` / `TRIM(BOTH ... FROM ...)`）；SQLite 与 PostgreSQL 支持 | MySQL 下直接语法错误 |

**影响面**：该函数被最近上传/下载、热门下载、排行榜等接口广泛调用（`upload_repo.go:350,363,391`、`services/monitor_service.go:139`），是后台统计与列表的核心过滤条件。

**整改建议**：

- 用 GORM 链式条件重写两个 `EXISTS` 分支，避免整段手写 WHERE；
- 若保留原生表达式：`||` 改用 `CONCAT('/', operation_records.full_path)`（三库通用），`TRIM(x, '/')` 改用 `TRIM(BOTH '/' FROM x)`（三库通用）；
- 表名改用 `models.FileRecordPublic{}.TableName()` / `models.OperationRecord{}.TableName()`。

### 3.2 `dedupGroupKey` —— `||` 与 `CAST(... AS TEXT)`

**文件**：`server/internal/repositories/upload_repo.go:336-339`

```go
dedupGroupKey := `(CASE WHEN file_record_id > 0
	THEN 'f' || CAST(file_record_id AS TEXT)
	ELSE 'p' || COALESCE(root_name,'') || COALESCE(file_path,'') || COALESCE(file_name,'')
	END)`
```

| 问题 | 方言事实 | 后果 |
|------|----------|------|
| 多处 `\|\|` 拼接 | MySQL 默认按逻辑 OR 解析 | 分组键计算错误 |
| `CAST(file_record_id AS TEXT)` | MySQL `CAST` 不接受 `TEXT`（应使用 `CHAR`） | MySQL 下语法错误 |

该字符串被 `Select(dedupGroupKey)`、`ROW_NUMBER() OVER (PARTITION BY ...)` 及子查询 `Table("(?) AS t", ...)`（第 346-370 行）共同使用，影响"最近上传/下载"分页去重逻辑。

**整改建议**：`||` → `CONCAT()`；`CAST(x AS TEXT)` → 用 GORM 表达式或 `CAST(x AS CHAR)`；并把表名改为模型 `TableName()`。

> 备注：同处的 `ROW_NUMBER() OVER (...)` 窗口函数在 SQLite 3.25+ / MySQL 8+ / PostgreSQL 均可用，本身不是阻塞项，但依赖上面的分组键修正。

### 3.3 `BackfillFileRecordIDs` —— `||` 拼接

**文件**：`server/internal/services/download_backfill.go:91-100`

	SET file_record_id = (

### 3.4 手写 `CREATE INDEX IF NOT EXISTS` DDL（MySQL 不支持）

**文件**：`server/internal/models/file_record.go`

```go
// 第 105 行（单列索引）
sql := "CREATE INDEX IF NOT EXISTS " + indexName + " ON " + table + "(" + idx.column + ")"
// 第 128 行（复合索引）
sql := "CREATE INDEX IF NOT EXISTS " + indexName + " ON " + table + "(" + idx.columns + ")"
// 第 137 行（唯一索引）
sql := "CREATE UNIQUE INDEX IF NOT EXISTS idx__file_records_private__share_code ON file_records_private(share_code)"
// 第 164 行（operation_records 索引）
sql := "CREATE INDEX IF NOT EXISTS " + indexName + " ON operation_records(" + idx.columns + ")"
```

| 问题 | 方言事实 | 后果 |
|------|----------|------|
| `CREATE INDEX IF NOT EXISTS` | **MySQL 不支持**该子句（MariaDB 才支持）；SQLite / PostgreSQL 支持 | MySQL 下报语法错误 |
| 失败仅 `db.Logger.Warn(...)` 后继续（第 106-109、129-131、138-140、165-167 行） | — | MySQL 部署下**所有索引静默未创建**，查询随数据量增长严重退化 |
| 第 152 行复合索引列含反引号 `` `action` `` | PostgreSQL 不支持反引号标识符 | PostgreSQL 下该索引创建失败 |

**整改建议**：统一改用 GORM Migrator（项目内已有正确范例——同文件 `CleanupOperationRecordIndexes` 使用 `HasIndex()` + `DropIndex()`）：

```go
if !db.Migrator().HasIndex(&models.OperationRecord{}, name) {
    _ = db.Migrator().CreateIndex(&models.OperationRecord{}, name)
}
```

或直接在模型字段上声明 `gorm:"index:..."` 交由 `AutoMigrate` 处理。同时移除列名中的反引号。

### 3.5 `EnsureSecurityEventIndexes` —— 手写 DDL + 标识符拼接

**文件**：`server/internal/models/security_event.go:64-74`

name := "idx__security_events__read_severity_created"

## 四、🟠 中危问题（PostgreSQL 下语法错误：反引号标识符）

PostgreSQL **不支持**反引号引用标识符（仅 SQLite 作为兼容扩展、MySQL 原生支持）。以下查询在 PostgreSQL 部署下会直接报语法错误：

| 文件:行号 | 片段 |
|-----------|------|
| `internal/repositories/upload_repo.go:318` | ``Where("`action` = ?", action)`` |
| `internal/repositories/upload_repo.go:348` | ``Where("`action` IN ?", ...)`` |
| `internal/repositories/upload_repo.go:361` | ``Where("`action` IN ?", ...)`` |
| `internal/repositories/upload_repo.go:390` | ``Where("`action` IN ?", ...)`` |
| `internal/repositories/upload_repo.go:400` | ``Where("`action` = ? AND ...")`` |
| `internal/repositories/upload_repo.go:422` | ``Where("id = ? AND `action` IN ?", ...)`` |
| `internal/repositories/upload_repo.go:438` | ``where := "deleted_at IS NULL AND `action` IN (?)"`` |
| `internal/repositories/upload_repo.go:471` | ``Where("`action` IN ?", ...)`` |
| `internal/repositories/upload_repo.go:498` | ``Where("`action` IN ?", ...)`` |
| `internal/repositories/url_download_task_repo.go:68` | ``Where("`status` = ?", status)`` |
| `internal/repositories/url_download_task_repo.go:121` | ``Where("id = ? AND (`status` = ? OR `status` = ?)", ...)`` |
| `internal/services/session_cleanup.go:18` | ``Where("`target_type` IN (?, '')", ...)`` |
| `internal/services/session_cleanup.go:20` | ``Where("`target_type` = ?", ...)`` |
| `internal/services/session_cleanup.go:28` | ``Where("`status` IN ? AND ...", ...)`` |
| `internal/services/session_cleanup.go:41` | ``Where("`status` = ? AND ...", ...)`` |
| `internal/services/admin_service.go:81` | ``Where("username LIKE ? OR `uuid` LIKE ?", ...)`` |
| `internal/models/file_record.go:152` | ``columns: "`action`, created_at"`` |

**整改建议**：`action` / `status` / `uuid` / `target_type` 在三种数据库中均**不是**需要转义的保留字，直接去掉反引号即可；如需转义，交由 GORM 处理，或使用 `clause.Column{Name: "action"}`（由方言自行决定引用符）。

## 九、附录：方言兼容性对照表

| 语法 / 函数 | SQLite | MySQL | PostgreSQL | 结论 |
|-------------|:------:|:-----:|:----------:|------|
| `\|\|` 字符串拼接 | ✅ | ❌（默认逻辑 OR） | ✅ | 禁用 |
| `CONCAT(a, b)` | ⚠️（3.44+ 才有） | ✅ | ✅ | 谨慎使用 |
| `TRIM(str, chars)` 两参数 | ✅ | ❌ | ✅ | 禁用 |
| `TRIM(BOTH c FROM str)` | ✅ | ✅ | ✅ | 可用 |
| `CAST(x AS TEXT)` | ✅ | ❌（需 `CHAR`） | ✅ | 禁用 |
| `CREATE INDEX IF NOT EXISTS` | ✅ | ❌ | ✅ | 禁用，改用 Migrator |
| 反引号 `` `col` `` | ✅ | ✅ | ❌ | 禁用 |
| `ROW_NUMBER() OVER (...)` | ✅（3.25+） | ✅（8.0+） | ✅ | 可用（需确认最低版本） |
| `COALESCE` / `CASE WHEN` / `EXISTS` / `GROUP BY` / `HAVING` | ✅ | ✅ | ✅ | 可用 |
| GORM `IN ?` / `IN (?)` 切片展开 | ✅ | ✅ | ✅ | 可用 |

> 表中方言事实来源：MySQL 官方 Bug #65540（不支持 `CREATE INDEX IF NOT EXISTS`）、MySQL Bug #101719（`TRIM(s, c)` 未支持，PostgreSQL/SQLite 支持）、SQLite 官方内置标量函数文档（`trim(X,Y)` 支持）。

## 十、审查方法说明

- 扫描方式：对 `server/` 全量 Go 源码检索 `db.Exec` / `db.Raw` / `db.Table(` / `gorm.Expr` / `fmt.Sprintf` 参与 SQL / 手写 DDL / 方言分支 / 反引号标识符 / 引擎专有函数。
- 判定口径：ORM 合规 / 原生 SQL 参数化且跨库兼容（可接受特殊情况）/ 方言专有（需整改）/ 标识符拼接（需整改）。
- 已对全部标记为"需整改"的关键位置逐行核对原始代码，并对涉及的方言事实做了外部核实。
