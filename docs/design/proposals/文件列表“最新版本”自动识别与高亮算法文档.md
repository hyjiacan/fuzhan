## 1. 背景

### 1.1 业务场景

系统是一个文件共享/网盘类产品。文件列表页中，同一目录下经常混放同一软件、同一份文档的多个版本。例如：

```text
Chrome 安装包目录：
chrome_stable_101.0.4951.54.exe
chrome_stable_102.0.4951.54.exe
chrome_beta_103.0.4951.54.exe

文档目录：
report.pdf
report(1).pdf
report(2).pdf
```

用户希望快速找到“最新可下载项”。如果列表里高亮多个文件，或者高亮错误文件，反而会干扰下载决策。因此需要一套自动识别规则，把“同一家族中版本最高的文件”高亮出来。

### 1.2 目标

- 输入：当前目录的一批文件记录，每条包含 `name`、`modifiedTime`、`path`、`type`。
- 输出：应高亮“最新版本”项的 `path` 集合（可能不止一个）。
- 约束：
  - 目录不参与；
  - 判定范围仅限当前目录，不做跨目录全局比较；
  - “同一家族”内只有 1 个文件时不标记；
  - 版本并列时必须用确定规则决出唯一；
  - 规则优先保证可解释、无歧义、易维护，其次才是覆盖极端命名。

### 1.3 核心判断

“最新版本”高亮本质是**相似文件名聚类 + 组内排序**问题，不是全目录版本号比较问题。只有先认定“这些文件名结构相似，属于同一家族”，才谈得上谁是最新版本。

因此算法分三阶段：

1. **结构相似性判定**：判断文件名是否属于同一家族；
2. **家族构建**：把当前目录切成若干家族；
3. **组内选最新**：在家族内部选版本最高者，并列时用确定性规则。

## 2. 问题定义

### 2.1 输入

```ts
type FileItem = {
  name: string          // 文件名，如 app_v1.2.3_windows_x64.exe
  modifiedTime: string  // 修改时间，ISO 字符串或可解析时间
  path: string          // 完整路径，作为唯一标识
  type: 'file' | 'dir' | 'directory'
}
```

### 2.2 输出

```ts
type Result = {
  latestPaths: Set<string>   // 应高亮的 path 集合
  groups: GroupInfo[]        // 可选，用于调试或 UI 提示
  confidence: number         // 可选，整体置信度
}

type GroupInfo = {
  signature: string   // 结构签名
  count: number       // 组内文件数
  bestPath: string    // 组内最新文件 path
  confidence: number  // 该组置信度
}
```

### 2.3 约束

- `type === 'dir'` 或 `'directory'` 的文件不参与；
- 组内文件数 < 2 时跳过（孤例不标记）；
- 版本并列时依次比较：预发布优先级 → 平台优先级 → 架构优先级 → 修改时间 → 文件名；
- 所有比较必须确定，不允许随机。

## 3. 方案选型

### 3.1 候选方案

| 方案 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| A. 全局版本解析 | 解析所有文件名版本，全局选最高 | 简单 | 不同产物混比，误高亮 |
| B. 基名 + 扩展名分组 | 剥版本、剥描述词得基名，分组比版本 | 可解释 | 剥错就分错族 |
| C. 结构签名分组 | 分段打标签，用结构签名分组 | 稳、可解释、O(n) | 需设计标签规则 |
| D. 相似度聚类 | 用编辑距离/余弦聚类 | 模糊匹配强 | 不可解释、O(n²)、资源重 |

### 3.2 选型结论

采用 **方案 C：结构签名分组 + 规则化版本比较**。

理由：

- 与“相似文件名结构才需标记”的业务判断一致；
- 每个文件只解析一次，分组 O(n)；
- 结构签名可输出为“结构模板”，结果可解释；
- 歧义点通过配置解决，不靠算法硬猜；
- 相似度算法仅作为可选辅助，不作为主判据。

### 3.3 相似度的定位

相似度算法（Jaccard、编辑距离）**不用于主流程**。仅在以下情况作为可选辅助：

- 离线评估结构签名覆盖率；
- 需要评估分组置信度；
- 规则完全失败时的兜底。

**不在运行时自动启用相似度**，因为编辑距离 O(n·m)、Jaccard 建集合，在上千文件场景下可能反而导致卡顿。是否启用由离线评估结果人工决定。

## 4. 算法设计

### 4.1 总体流程

```mermaid
flowchart TD
  A[输入 files + config] --> B[单次遍历: 提取扩展名]
  B --> C[原子 token 提取: 版本/日期/括号序号]
  C --> D[剩余部分按分隔符切分]
  D --> E[合并 token 序列, 打标签]
  E --> F[生成结构签名]
  F --> G[Map 分组 O(n)]
  G --> H[组内选最新 O(n)]
  H --> I[计算每组置信度]
  I --> J[输出 latestPaths + groups + confidence]
```

### 4.2 扩展名提取

支持双扩展名，列表可配置：

```js
const DEFAULT_MULTI_EXTS = [
  '.tar.gz', '.tar.bz2', '.tar.xz', '.tar.zst',
  '.tar.lz', '.tar.lzma'
]

function extractExt(name, multiExts = DEFAULT_MULTI_EXTS) {
  const lower = name.toLowerCase()
  for (const ext of multiExts) {
    if (lower.endsWith(ext)) return ext
  }
  const i = lower.lastIndexOf('.')
  return i > 0 ? lower.slice(i) : ''
}
```

### 4.3 原子 token 提取

v1 的缺陷根源是：先按 `SEP` 切分，再打标签，导致点分版本、日期、括号序号在切分阶段就被破坏。

v2 改为：**先提取原子 token，再切分剩余部分，最后按原位置合并**。

原子 token 类型：

| 类型 | 正则 | 示例 |
|---|---|---|
| 点分版本 | `v?\d+(\.\d+){1,5}` | `v1.2.3`、`1.2.3.4` |
| 日期 | `\d{4}-\d{2}-\d{2}` 或 `\d{8}` | `2024-01-02`、`20240101` |
| 括号序号 | `[\[(]\d+[\])]` | `(1)`、`[2]` |

```js
const ATOM_PATTERNS = [
  { type: 'DATE', re: /\d{4}-\d{2}-\d{2}|\d{8}/g, validate: validateDate },
  { type: 'PAREN', re: /[\[(]\d+[\])]/g, validate: null },
  { type: 'VERSION', re: /v?\d+(\.\d+){1,5}/gi, validate: null }
]

function validateDate(s) {
  let y, m, d
  if (s.includes('-')) {
    [y, m, d] = s.split('-').map(Number)
  } else {
    y = Number(s.slice(0, 4))
    m = Number(s.slice(4, 6))
    d = Number(s.slice(6, 8))
  }
  if (m < 1 || m > 12) return false
  if (d < 1 || d > 31) return false
  return true
}

function extractAtoms(stem) {
  const atoms = []
  for (const { type, re, validate } of ATOM_PATTERNS) {
    re.lastIndex = 0
    let m
    while ((m = re.exec(stem))) {
      const text = m[0]
      if (validate && !validate(text)) continue
      atoms.push({ type, text, start: m.index, end: m.index + text.length })
    }
  }
  atoms.sort((a, b) => a.start - b.start || b.end - a.end)
  const filtered = []
  let lastEnd = -1
  for (const a of atoms) {
    if (a.start >= lastEnd) {
      filtered.push(a)
      lastEnd = a.end
    }
  }
  return filtered
}
```

### 4.4 分词与合并

```js
const SEP = /[_\-.\[\]()\s]+/

function tokenize(name, config) {
  const ext = extractExt(name, config.multiExts)
  const stem = name.slice(0, name.length - ext.length)

  const atoms = extractAtoms(stem)
  const tokens = []
  let cursor = 0

  for (const atom of atoms) {
    if (atom.start > cursor) {
      const gap = stem.slice(cursor, atom.start)
      for (const p of gap.split(SEP)) {
        if (p) tokens.push({ type: 'RAW', text: p })
      }
    }
    tokens.push({ type: atom.type, text: atom.text })
    cursor = atom.end
  }
  if (cursor < stem.length) {
    const gap = stem.slice(cursor)
    for (const p of gap.split(SEP)) {
      if (p) tokens.push({ type: 'RAW', text: p })
    }
  }

  return { ext, tokens }
}
```

### 4.5 打标签

原子 token 直接使用其类型；RAW token 按规则判断：

```js
const DESCRIPTORS = {
  channel: new Set(['stable','beta','alpha','dev','canary','nightly','preview','release','rc']),
  platform: new Set(['windows','macos','linux','ubuntu','debian','centos','freebsd','darwin','win32','win64','osx','win','mac']),
  arch: new Set(['x86-64','x86_64','i386','i486','i686','x86','x64','64bit','32bit','64-bit','32-bit','arm64','aarch64','amd64','arm'])
}

function tagToken(token) {
  if (token.type === 'VERSION') return 'V'
  if (token.type === 'DATE') return 'D'
  if (token.type === 'PAREN') return 'P'
  const lower = token.text.toLowerCase()
  if (DESCRIPTORS.channel.has(lower)) return 'WC'
  if (DESCRIPTORS.platform.has(lower)) return 'WP'
  if (DESCRIPTORS.arch.has(lower)) return 'WA'
  if (/^\d+$/.test(token.text)) return 'N'
  return 'T'
}
```

### 4.6 结构签名（v2.2 修改）

v2.1 的 `signature` 只把 `T` 标签放入 `subjects`，导致 `WA`/`WP`/`WC` 的具体词不参与签名，不同架构/平台/通道仍会同族。

v2.2 引入三态配置：

| 配置 | 取值 | 含义 |
|---|---|---|
| `channelGrouping` | `merge` / `separate` / `rank` | 通道合并 / 各自成族 / 合并但按通道排序 |
| `platformGrouping` | `merge` / `separate` / `rank` | 平台合并 / 各自成族 / 合并但按平台排序 |
| `archGrouping` | `merge` / `separate` / `rank` | 架构合并 / 各自成族 / 合并但按架构排序 |

- `merge`：从签名中剔除该标签，所有值同族。
- `separate`：该标签的具体词放入 `subjects`，不同值成不同族。
- `rank`：从签名中剔除该标签，同族，但同版本时按优先级排序。

```js
function signature(name, config) {
  const { ext, tokens } = tokenize(name, config)
  const tags = tokens.map(tagToken)
  const subjects = []
  const filteredTags = []

  for (let i = 0; i < tokens.length; i++) {
    const tag = tags[i]
    const lower = tokens[i].text.toLowerCase()

    if (tag === 'WC') {
      if (config.channelGrouping === 'merge' || config.channelGrouping === 'rank') continue
      if (config.channelGrouping === 'separate') subjects.push(lower)
    } else if (tag === 'WP') {
      if (config.platformGrouping === 'merge' || config.platformGrouping === 'rank') continue
      if (config.platformGrouping === 'separate') subjects.push(lower)
    } else if (tag === 'WA') {
      if (config.archGrouping === 'merge' || config.archGrouping === 'rank') continue
      if (config.archGrouping === 'separate') subjects.push(lower)
    } else if (tag === 'T') {
      subjects.push(lower)
    }
    filteredTags.push(tag)
  }

  return `${filteredTags.join('')}|${subjects.join('_')}|${ext}`
}
```

示例：

```text
# archGrouping = 'separate'
app-1.0-x64.exe → sig: "TVWA|app_x64|.exe"
app-2.0-x64.exe → sig: "TVWA|app_x64|.exe"   同族
app-1.0-x86.exe → sig: "TVWA|app_x86|.exe"
app-2.0-x86.exe → sig: "TVWA|app_x86|.exe"   同族
# x64 和 x86 各自独立选最新

# archGrouping = 'merge'
app-1.0-x64.exe → sig: "TVWA|app|.exe"
app-2.0-x64.exe → sig: "TVWA|app|.exe"
app-1.0-x86.exe → sig: "TVWA|app|.exe"
app-2.0-x86.exe → sig: "TVWA|app|.exe"
# 四个同族，同版本时按 archRank 决出 x64

# archGrouping = 'rank'
# 同 merge，但同版本时按 archRank 排序，效果等价
```

### 4.7 版本解析

版本解析与预发布标记统一在 token 序列上进行：

```js
const PRE_RANK = { rc: 3, beta: 2, alpha: 1, preview: 1, dev: 0, nightly: 0, canary: 0 }

function extractVersion(tokens) {
  for (let i = 0; i < tokens.length; i++) {
    if (tokens[i].type === 'VERSION') {
      const text = tokens[i].text.replace(/^v/i, '')
      return { parts: text.split('.').map(Number), index: i, source: 'VERSION' }
    }
  }
  for (let i = 0; i < tokens.length; i++) {
    if (tokens[i].type === 'PAREN') {
      const num = Number(tokens[i].text.replace(/[\[()\]]/g, ''))
      return { parts: [num], index: i, source: 'PAREN' }
    }
  }
  for (let i = 0; i < tokens.length; i++) {
    if (tokens[i].type === 'DATE') {
      const t = tokens[i].text
      if (t.includes('-')) {
        return { parts: t.split('-').map(Number), index: i, source: 'DATE' }
      }
      return {
        parts: [Number(t.slice(0,4)), Number(t.slice(4,6)), Number(t.slice(6,8))],
        index: i, source: 'DATE'
      }
    }
  }
  for (let i = tokens.length - 1; i >= 0; i--) {
    if (tokens[i].type === 'RAW' && /^\d+$/.test(tokens[i].text)) {
      return { parts: [Number(tokens[i].text)], index: i, source: 'NUM' }
    }
  }
  return null
}

function extractPre(tokens, versionIndex) {
  if (versionIndex == null) return null
  for (let i = versionIndex + 1; i < tokens.length; i++) {
    const lower = tokens[i].text.toLowerCase()
    const m = lower.match(/^(rc|beta|alpha|preview|dev|nightly|canary)(?:[.\-]?(\d+))?$/)
    if (m) {
      return { tag: m[1], num: m[2] ? Number(m[2]) : 0 }
    }
  }
  return null
}
```

### 4.9 分组

```js
function groupFiles(files, config) {
  const groups = new Map()

  for (const file of files) {
    if (file.type === 'dir' || file.type === 'directory') continue
    const parsed = parseFile(file, config)
    const key = parsed.signature
    if (!groups.has(key)) groups.set(key, [])
    groups.get(key).push(parsed)
  }

  return groups
}

function parseFile(file, config) {
  const { ext, tokens } = tokenize(file.name, config)
  const tags = tokens.map(tagToken)
  const sig = signature(file.name, config)
  const ver = extractVersion(tokens)
  const pre = extractPre(tokens, ver?.index)
  const platform = extractPlatform(tokens)
  const arch = extractArch(tokens)

  return { file, ext, tokens, tags, signature: sig, ver, pre, platform, arch }
}
```

### 4.10 组内选最新

```js
function pickLatest(group, config) {
  if (group.length < 2) return null
  let best = group[0]
  for (let i = 1; i < group.length; i++) {
    if (compareItem(group[i], best, config) > 0) best = group[i]
  }
  return best
}

function compareItem(a, b, config) {
  const va = a.ver ? a.ver.parts : [0]
  const vb = b.ver ? b.ver.parts : [0]
  const cmp = compareParts(va, vb)
  if (cmp !== 0) return cmp

  const pa = a.pre ? PRE_RANK[a.pre.tag] : 4
  const pb = b.pre ? PRE_RANK[b.pre.tag] : 4
  if (pa !== pb) return pa - pb
  const na = a.pre?.num || 0
  const nb = b.pre?.num || 0
  if (na !== nb) return na - nb

  const ra = config.platformRank[a.platform] ?? 0
  const rb = config.platformRank[b.platform] ?? 0
  if (ra !== rb) return ra - rb

  const aa = config.archRank[a.arch] ?? 0
  const ab = config.archRank[b.arch] ?? 0
  if (aa !== ab) return aa - ab

  const ta = new Date(a.file.modifiedTime || 0).getTime()
  const tb = new Date(b.file.modifiedTime || 0).getTime()
  if (ta !== tb) return ta - tb

  return a.file.name.localeCompare(b.file.name)
}

function compareParts(a, b) {
  const len = Math.max(a.length, b.length)
  for (let i = 0; i < len; i++) {
    const x = a[i] || 0, y = b[i] || 0
    if (x !== y) return x - y
  }
  return 0
}
```

function analyzeLatestVersions(files, userConfig = {}) {
  const config = buildConfig(userConfig)
  const groups = groupFiles(files, config)
  const latestPaths = new Set()
  const groupInfos = []

  for (const [sig, group] of groups) {

      signature: sig,
      count: group.length,
      bestPath: best.file.path,

  }
}

## 6. 歧义点处理建议

| 歧义点 | 建议 | 理由 |
|---|---|---|
| ① 通道合并 | 默认 `merge`，正式版同版本优先 | 用户通常找最新正式版 |
| ② 平台/架构合并 | 默认 `rank`，同版本时按平台→架构→时间→文件名排序 | 避免多个高亮，排序可解释；需要各自独立时设 `separate` |
| ③ 扩展名分组 | 默认作为分组维度，各自高亮 | `.zip` 与 `.exe` 是不同产物 |
| ④ 孤例 | 默认不标记，可选 `includeLone` | 孤例无“最新”语义 |
| ⑤ 有版本优先 vs 时间回退 | 保留，无版本文件视为版本 `[0]` 参与比较 | 避免正式版被排除 |
| ⑥ 预发布 | 数值版本相同则正式版优先，预发布按 rc > beta > alpha | 符合语义化版本习惯 |

## 8. 复杂度与瓶颈

### 8.1 时间复杂度

设 `n` 为文件数，`L` 为文件名平均长度，`t` 为 token 数（`t ≤ L`），`g` 为组数，`k` 为最大组内文件数。

| 阶段 | 复杂度 |
|---|---|
| 单文件解析 | O(L) |
| 总解析 | O(n·L) |
| 分组 | O(n) |
| 组内选最新 | O(k)，总 O(n) |
| 总 | **O(n·L)** |

### 8.2 空间复杂度

| 结构 | 空间 |
|---|---|
| 解析结果 | O(n·t) |
| 分组 Map | O(n + g) |
| 输出集合 | O(g) |
| 总 | **O(n·t)**，`t ≤ L` |

### 8.3 瓶颈

| 排名 | 瓶颈 | 占比 | 缓解方向 |
|---|---|---|---|
| 1 | 单文件解析 | ~70% | 合并正则、快速预判、字符串扫描 |
| 2 | 字符串操作与 GC | ~15% | 减少 split、复用数组 |
| 3 | 正则引擎 | ~10% | 预编译、合并、替代 |
| 4 | 分组 Map 键 | ~5% | 数字 ID、粗分组 |
| — | 分组、比较、输出 | < 5% | 无需优化 |

**结论：瓶颈在单文件解析 O(n·L)，分组和比较都是 O(n)，不是瓶颈。**

### 8.4 规模估算

| 文件数 | 耗时 | 内存 |
|---|---|---|
| 1000 | 50~150ms | < 1MB |
| 5000 | 250~750ms | < 5MB |
| 10000 | 0.5~1.5s | < 10MB |

## 9. 置信度模型

置信度 = 算法对“这个高亮结果正确”的把握程度，取值 0~1。按组计算，整体取加权平均。

| 信号 | 权重 | 含义 |
|---|---|---|
| 结构一致性 | 0.35 | 同族内签名完全一致 |
| 版本可解析性 | 0.30 | 同族内有版本号的文件比例 |
| 版本区分度 | 0.20 | 最高与次高版本是否有明确差距 |
| 数据完整性 | 0.15 | `name`/`path`/`modifiedTime` 齐全 |

```js
function computeConfidence(group) {
  const sigSet = new Set(group.map(g => g.signature))
  const consistency = sigSet.size === 1 ? 1 : 1 / sigSet.size

  const withVer = group.filter(g => g.ver).length
  const parseability = withVer / group.length

  const sorted = group.filter(g => g.ver).sort((a, b) => compareParts(b.ver.parts, a.ver.parts))
  let distinctness = 0
  if (sorted.length >= 2) {
    const top = sorted[0].ver.parts
    const second = sorted[1].ver.parts
    distinctness = compareParts(top, second) !== 0 ? 1 : 0.5
  } else if (sorted.length === 1) {
    distinctness = 0.3
  }

  const complete = group.filter(g => g.file.name && g.file.path && g.file.modifiedTime).length
  const integrity = complete / group.length

  return 0.35 * consistency
       + 0.30 * parseability
       + 0.20 * distinctness
       + 0.15 * integrity
}

function overallConfidence(groups) {
  let total = 0, weight = 0
  for (const g of groups.values()) {
    total += computeConfidence(g) * g.length
    weight += g.length
  }
  return weight ? total / weight : 0
}
```

### 9.1 典型场景参考值

| 场景 | 置信度 |
|---|---|
| `app_v1.2.3.exe`, `app_v2.0.exe` | 0.95+ |
| `app-2.zip`, `app-10.zip` | 0.90 |
| `report.pdf`, `report(1).pdf`, `report(2).pdf` | 0.75 |
| `chrome_stable_1.2.3.exe`, `chrome_beta_1.3.0.exe` | 0.85 |
| `app_windows.exe`, `app_linux.exe` | 0.55 |
| `x64studio.7z`, `office2021.zip` | 0.60 |
| `backup-20240101.zip`, `backup-2024-01-02.zip` | 0.70 |

### 9.2 使用方式

| 置信度 | 建议行为 |
|---|---|
| ≥ 0.85 | 正常高亮 |
| 0.70 ~ 0.85 | 高亮，可加“疑似”提示 |
| 0.50 ~ 0.70 | 不高亮，或仅在“显示所有版本”时标记 |
| < 0.50 | 不标记，避免误导 |

阈值可配置。

## 10. 不做什么

本算法明确**不覆盖**以下场景，避免使用者预期偏差：

- **跨目录比较**：只在当前目录内比较，不做全局最新版本。
- **语义化版本的不规范变体**：如 `1.2.3.4.5.6.7` 这种超长版本号，按数值比较，不按语义化版本规范校验。
- **Git 描述版本**：如 `v1.2.3-5-gabc1234`，`gabc1234` 不被解析为版本。
- **构建号与版本号混用**：如 `1.2.3+build.456`，`+` 后部分不参与比较。
- **主体词语义理解**：如 `office2021` 中 `2021` 是版本还是产品名，算法按位置和格式判断，不保证语义正确。
- **通道/平台/架构的自动合并策略**：由配置决定，算法不自动推断。
- **孤例的高亮**：默认不标记，除非 `includeLone` 为 true。
- **相似度自动兜底**：不在运行时自动启用，由离线评估人工决定。
- **跨语言/跨平台命名习惯**：如中文名、日文名、非 ASCII 字符，算法按通用分隔符处理，不保证最佳效果。
- **文件内容差异**：只看文件名和修改时间，不读文件内容，不判断文件是否损坏、是否可执行。
- **权限与可见性**：不做权限过滤，由调用方在传入 `files` 前处理。
- **版本号语义正确性**：如 `1.0.0` 是否比 `1.0` 新，按补零规则视为相等，不按语义化版本规范额外判断。
- **预发布序号语义**：如 `beta.10` 与 `beta.9`，按数值比较，`10 > 9`，正确；但不处理 `beta.1a` 这类非纯数字序号。
- **缓存、Worker、中断等工程措施**：算法本身是纯函数，无状态，这些由调用方决定，见第 11 章。

## 12. 工程实施建议与示例

本章为调用方提供落地参考。算法本身不依赖这些措施，但合理使用能显著改善体验。

### 12.1 核心原则

| 原则 | 说明 |
|---|---|
| 算法纯函数 | 不依赖全局状态，输入相同则输出相同 |
| 不阻塞首屏 | 列表先渲染，高亮异步后到 |
| 结果可丢弃 | 切换目录时旧结果直接丢，不保证送达 |
| 失败可降级 | 算不出来就不高亮，不报错 |
| 低置信度不标记 | 置信度低于阈值时不高亮，避免误导 |

### 12.2 推荐架构

```text
用户进入目录
  ↓
列表立即渲染（不高亮）
  ↓
后台发任务给 Worker
  ↓
Worker 解析 → 分组 → 选最新 → 计算置信度
  ↓
主线程收到结果，检查 requestId 与目录
  ↓
若目录未变，按置信度高亮；若已切换，丢弃
```

### 12.3 主线程示例

```js
let currentRequestId = 0
let currentDir = null
let worker = new Worker('analyzer.js')

function onDirectoryEnter(dir, files, config) {
  currentDir = dir
  const requestId = ++currentRequestId

  // 1. 列表先渲染，不高亮
  renderList(files)

  // 2. 后台异步分析
  worker.postMessage({
    type: 'analyze',
    requestId,
    dir,
    files: files.map(f => ({
      path: f.path,
      name: f.name,
      modifiedTime: f.modifiedTime,
      type: f.type
    })),
    config
  })
}

worker.onmessage = e => {
  // 丢弃过期结果
  if (e.data.requestId !== currentRequestId) return
  if (e.data.dir !== currentDir) return

  // 按置信度决定是否高亮
  const paths = e.data.latestPaths.filter(p => {
    const c = e.data.confidences[p]
    return c >= 0.7
  })

  requestAnimationFrame(() => renderHighlight(paths))
}
```

### 12.4 Worker 示例

```js
let latestRequestId = 0

self.onmessage = e => {
  if (e.data.type !== 'analyze') return

  latestRequestId = e.data.requestId
  const { requestId, dir, files, config } = e.data

  const result = analyzeLatestVersions(files, config)

  // 被新任务取代，丢弃
  if (requestId !== latestRequestId) return

  const confidences = {}
  for (const g of result.groups) {
    confidences[g.bestPath] = g.confidence
  }

  self.postMessage({
    type: 'result',
    requestId,
    dir,
    latestPaths: [...result.latestPaths],
    confidences
  })
}
```

### 12.5 缓存策略

缓存不是必须的。按场景决定：

| 场景 | 建议 |
|---|---|
| 主要交互是切换目录 | 不缓存，或只缓存当前目录 |
| 同一目录内频繁排序/筛选/刷新 | 缓存当前目录，切换时清空 |
| 列表增量加载 | 缓存已解析文件，只解析新增 |
| 配置频繁变化 | 按 cacheKey 隔离，或不用缓存 |
| 内存敏感环境 | 不用缓存 |

**最简单的落地：只缓存当前目录，切换目录时清空。**

```js
let currentDir = null
let currentCache = new ParseCache(2000)

function onDirectoryChange(newDir) {
  if (newDir !== currentDir) {
    currentCache.clear()
    currentDir = newDir
  }
}
```

### 12.6 中断策略

中断是必须的。否则旧任务浪费 CPU，新任务排队，UI 收到过期结果。

| 层面 | 实现 | 必要性 |
|---|---|---|
| 主线程丢弃过期结果 | `requestId` 检查 | 必须 |
| Worker 内部检查 | `latestRequestId` 检查 | 建议 |
| 防抖合并快速切换 | `setTimeout` 150ms | 建议 |
| Worker 终止重建 | `worker.terminate()` | 仅超时或无法快速中断时 |

```js
let debounceTimer

function onDirectoryChange(files, config) {
  clearTimeout(debounceTimer)
  debounceTimer = setTimeout(() => {
    analyze(files, config)
  }, 150)
}
```

### 12.7 性能阈值建议

| 文件数 | 执行位置 | 缓存 | 分片 | 防抖 |
|---|---|---|---|---|
| < 100 | 主线程 | 不需要 | 否 | 可选 |
| 100~500 | 主线程或 Worker | 可选 | 可选 | 150ms |
| 500~1000 | Worker | 可选 | 可选 | 150ms |
| 1000~5000 | Worker | 可选 | 是 | 150ms |
| 5000~10000 | Worker | 建议 | 是 | 200ms |
| > 10000 | Worker | 必须或增量 | 是 | 200ms |

## 13. 结论

### 13.1 核心结论

1. **采用“结构签名分组 + 规则化版本比较”**，不用相似度作主判据。
2. **算法整体 O(n·L)**，空间 O(n·t)，主项是单文件解析。
3. **歧义点通过三态配置解决**（`merge` / `separate` / `rank`），不靠算法硬猜。
4. **结果可解释**：每个族有结构模板，每个高亮有比较依据。
5. **输出置信度**：按结构一致性、版本可解析性、版本区分度、数据完整性计算。
6. **算法本身不关心工程措施**：缓存、Worker、中断由调用方决定，第 12 章给出实施建议。

### 13.2 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 主判据 | 结构签名 | 可解释、O(n)、与业务判断一致 |
| 分词策略 | 先提取原子 token，再切分剩余 | 避免点分版本、日期、括号序号被破坏 |
| 版本比较 | 数值逐段比较，短版本补零 | 符合版本号直觉，`12.1 > 2.1` |
| 预发布 | 数值相同则正式版优先 | 符合语义化版本习惯 |
| 孤例 | 默认不标记 | 孤例无“最新”语义 |
| 扩展名 | 作为分组维度 | `.zip` 与 `.exe` 是不同产物 |
| 通道/平台/架构 | 三态配置：`merge` / `separate` / `rank` | 避免“默认混在一起”的歧义 |
| 相似度 | 主流程不用 | 不可解释、O(n²)、资源重 |
| 置信度 | 按组计算，整体加权平均 | 低置信度不标记 |

### 13.3 后续演进

1. **元数据优先**：文件记录有 `version` 字段时直接使用，不解析文件名。
2. **手动标记**：允许用户指定“最新版本”，作为兜底。
3. **规则配置化**：允许管理员扩展描述词表、版本模式、优先级。
4. **相似度辅助**：离线评估结构签名覆盖率，低于阈值时人工决定是否启用。
5. **多语言命名**：扩展分隔符和描述词表，支持非 ASCII 命名。

### 13.4 一句话总结

> **把“最新版本”高亮当成“相似文件名聚类 + 组内排序”问题，用结构签名分组、规则化版本比较、三态配置处理通道/平台/架构歧义、置信度模型评估结果可信度，就能以 O(n·L) 时间、O(n·t) 空间、可解释、可维护地解决大多数常见命名。算法本身是纯函数，缓存、Worker、中断等工程措施由调用方决定，第 12 章给出实施建议与示例。**
