## 二、代码审查发现

### 2.1 严重

1. **API 日志脱敏在大请求体下完全失效（密钥明文落盘）** — `server/internal/middleware/api_activity.go:134-140,161-176`
   `captureJSONBody` 只读取 `maxAPICaptureBytes+1`（2049）字节，超过即为**截断后的非法 JSON**，`sanitizeJSON` 的 `json.Unmarshal` 必然失败，于是走 fallback `truncateUTF8(string(raw))`（168/173 行）**直接输出原始字节，不经过 `redactSensitive`**。典型受影响请求为 `POST /api/v1/config`（请求体必然 >2KB，且含 `jwt_secret`、`auth.ldap.bind_password`）——与提交声称的「敏感字段脱敏」直接矛盾。**修复建议**：解析失败时也不得回退原文，应做正则/流式擦除，或干脆不记录无法解析的 body。

2. **敏感字段名缺失，配置密钥本就漏记** — `server/internal/middleware/api_activity.go:20-36`
   `sensitiveKeys` 为精确小写匹配，未包含 `jwt_secret`、`bind_password`（仅 `jwt`/`secret`/`client_secret` 命中）。即使 body 很小、解析成功，`server.jwt_secret` 与 `auth.ldap.bind_password` 仍会明文写日志。**修复建议**：补全字段名或改为「键名包含敏感子串」匹配。

3. **手动重试会误删共享目录中他人文件** — `server/internal/file/url_task_handlers.go:552-557`（`RetryURLTask`）
   重试前无条件 `os.Remove(task.TargetPath)`。目标路径由「根目录+目录+文件名」确定性生成，公共目录中同名文件可能属于他人；当任务正是因「目标文件已存在」而失败时，用户点重试会直接删掉**别人的现有文件**。**修复建议**：仅在确认该目标由本任务创建时才删除（校验 OperationRecord/索引归属），否则交由 worker 在 finalize 时按上传者 IP 规则处理。

4. **任务状态跃迁非原子、缺守卫** — `server/internal/repositories/url_download_task_repo.go:138-147`（`RequeueForRetry`，`Where("id = ?")` 无状态条件）+ `server/internal/file/url_task_handlers.go:428-440`
   `CancelURLTask` 允许取消 `downloading` 任务，但 `RequeueForRetry` 只按 `id` 写回 `pending`；`failURLTask` 的 `UpdateStatus(failed)`（`url_download.go:197`）与 finalize 的 `UpdateStatus(completed)`（`url_download.go:629`）同样无守卫。结果：失败重排会**复活已取消任务**，或成功路径把 `cancelled` 覆盖成 `completed`。**修复建议**：所有状态写入加 `WHERE status = <期望前置状态>`，取消与完成互斥。（对照：`ResetToPending` 已带状态守卫，做法正确。）

### 2.2 重要

5. **取消无法真正中断进行中的下载** — `server/internal/file/url_task_handlers.go:438-440`
   取消时 `os.Remove(task.TempFilePath)` 与正在写文件的 worker 竞争：Windows 下文件被占用删除静默失败、下载继续；Linux 下 inode 被 unlink，worker 继续写，finalize `os.Rename` 失败 → 任务变 `failed` 且无产物。**修复建议**：引入按任务的 context 取消或删除标记，由 worker 感知后自行中止并清理。

6. **`status` 字段无索引，调度热路径全表扫描** — `server/internal/models/url_download_task.go:37`
   `ClaimNextPending`（repo:190-191）以 `WHERE status='pending' ORDER BY queued_at, created_at` 执行，而调度器在每次 `Notify` **及每秒 ticker** 都会调用；终态行从不清理、表持续增长。**修复建议**：加复合索引 `(status, queued_at)`。

7. **全局配置读取存在数据竞争** — `server/internal/file/url_dispatcher.go:42`、`server/internal/file/url_download.go:158`
   直接读 `appconfig.GlobalConfig.Upload.URLUpload.MaxConcurrent/MaxRetries`，未持 `configMu.RLock`；而 `SaveConfig`（`config/handler.go:136`）在写锁下原地修改 `GlobalConfig`。**修复建议**：改用 `appconfig.GetConfig()` / `RLockConfig()`。

8. **关键状态写入错误被吞、worker 入口无 recover** — `server/internal/file/url_download.go:205,221,229,264,286,628-629`
   多处 `_ = UpdateStatus(...)` 忽略错误；DB 写失败会让任务永久停留在 `downloading`。且 `executeURLDownloadTask`（`url_download.go:203`）自身无 recover，其内部 panic 会直接崩溃进程（recover 仅在 `downloadFromURL` 内）。**修复建议**：关键状态写入失败时记录并补偿，worker 入口加 recover。

9. **5xx 日志明文记录查询串中的 token** — `server/internal/utils/error_handler.go:78-80`
   `HandleError` 把 `c.Request.URL.RawQuery` 原样写入日志，而 `AuthRequired` 支持 `?token=`（`middleware/auth.go:96`），JWT 会明文进入保留 30 天的 error.log，且未经 `sanitizeQuery`。**修复建议**：复用/导出 `sanitizeQuery`，至少对 `token/access_token` 打码。

10. **渠道日志器存在数据竞争 / 关闭后写入** — `server/internal/utils/logger.go:61-63,104-112,304-346`
    `AppLogger/ErrorLogger/AccessLogger/channelLoggerOf` 读取 `globalLogManager` 指针时未持 `globalLogMu`，而 `InitLogger/ReinitLogger/CloseLogger` 在锁内改写指针并 `close()` 关闭 writer。热重载/退出时并发写日志会写到已关闭文件或丢日志（`-race` 可复现）。**修复建议**：用 `atomic.Pointer` 或统一持锁读取，先换指针再异步关闭旧 writer。

11. **日志 `user_id` 字段为死代码** — `server/internal/middleware/monitoring.go:116`、`server/internal/utils/error_handler.go:68`
    读取 `ContextKeyUserID`（"userID"，仅 API Key 认证以 `uint` 写入）并断言 `.(string)`，而 JWT 认证写的是 `ContextKeyUserUUID`（"userUUID"）。断言恒失败 → 承诺的 `user_id` 从不出现。**修复建议**：改读 `ContextKeyUserUUID`（string），并兼容 uint。

12. **`sanitizeQuery` 解析失败时回退原文** — `server/internal/middleware/api_activity.go:148-151`
    `url.ParseQuery` 出错即 `return rawQuery`，非法转义会让 token 明文进日志；且仅匹配顶层键（`filter[token]` 之类不覆盖）。**修复建议**：失败时正则兜底擦除。

### 2.3 次要

13. **重启对账的窄窗口丢失完成态** — `server/main.go:412-440`、`server/internal/file/url_download.go:469,629`
    进程在 finalize 的 `os.Rename` 之后、`UpdateStatus(completed)` 之前退出 → 重启后任务被重排并因「目标已存在」判失败，文件已落盘但无操作记录/索引。且 `RequeueInterrupted` 未重置 `downloaded_bytes`，`main.go:417-425` 删除半截文件却保留旧进度。

14. **重试无退避** — `server/internal/file/url_download.go:177-199`
    可重试失败立即重排，有空槽即被领回，持续失败的远端会连续耗尽全部重试。次数有上限（实际尝试 = 1 + maxRetries，无 off-by-one/死循环）。**修复建议**：加最小重试间隔。

15. **删除任务不中断进行中的 worker** — `server/internal/file/url_task_handlers.go:569-594`、`server/internal/admin/url_download_handler.go:100-110`
    删除 DB 行后 worker 仍会生成目标文件与操作记录（孤儿文件）。另 admin 删除临时任务时用 `temp.Path + "/" + task.TargetPath` 二次拼接（`TargetPath` 已是绝对路径），路径错误、删不掉。

16. **admin 重试未唤醒调度器** — `server/internal/admin/url_download_handler.go:81`
    管理员重试 `ResetToPending` 后未 `dispatcher.Notify()`，依赖 1s ticker，最多延迟 1 秒；与用户侧 `RetryURLTask` 行为不一致。

17. **响应截断静默** — `server/internal/middleware/api_activity.go:52,65-79,90-111`
    `truncated` 标志只写不读；响应 >2048 字节时 `finish` 解析失败 → `result` 静默为空，日志无法区分「无数据」与「已截断」。

18. **页脚健康状态延迟最长 8s** — `ui/src/App.vue:54-66`、`ui/src/components/common/AppFooter.vue:159`
    页脚改为复用 `store.state.health`，但该值在 `requestIdleCallback(timeout:8000)` 后才拉取，此前页脚显示 `unknown`/`—`，属行为回退。**修复建议**：`store.state.health` 为空时允许页脚兜底请求。

19. **过度脱敏** — `server/internal/middleware/api_activity.go:35`
    通用键 `"key"` 会误伤正常字段（排序键/响应数据）。**修复建议**：收窄匹配。
