1. 结论速览

整体架构健康且成熟，作者对 SQLite 单写者模型、watch 事件去抖、有界异步审计、覆盖索引等约束有充分考量。下载主路径已使用 http.ServeFile 流式传输（支持 Range / 206 / sendfile），URL 转存采用分块预分配。主要性能欠账集中在两条热路径：数据库通配符全文搜索与串行目录全量索引扫描，其余为可优化的常量因子与写放大开销。

3. 高风险问题

高数据库搜索通配符全表扫描，file_name 无索引可用services/search_service.go:117 · models/file_record.go:87-142
现象
关键词过滤使用前导通配的 LIKE '%kw%'（同时匹配文件名与备注），且三张索引表建立的全部单列/复合索引均不含 file_name 列（见 file_record.go:91-141）。即便存在 file_name 索引，前导通配符也无法命中。
影响
文件量增大后每次搜索都要对 filtered 结果集做整表级扫表，占用 SQLite 读锁；为缓解并发已回退为单查询（避免多 goroutine 加剧锁竞争，见 :103-104），但这只是抑制了并发放大，未能降低单次扫描成本。
方向
改为前缀匹配（name LIKE 'kw%'）+ (root_name,status,file_name) 覆盖索引；或引入词项检索 / SQLite FTS5（已内置，可作为 file_records_* 的外置词表），从根本上消除前导通配扫表。
高全量索引扫描双重 Walk + 单协程顺序递归internal/index/scanner_public.go:35,239 · scanner.go
现象
先 countFiles 完整 Walk 整棵目录树做纯统计，随后 scanRootDir 再 filepath.Walk 第二次；且 filepath.Walk 为单协程深度优先，仅在多个根目录之间并行。
影响
大而深的目录树全量扫描成为单点瓶颈，首次建索引 / 重启重建耗时随文件数线性增长且无法利用多核（哈希 worker 虽并发，但被串行的目录遍历拖住）。
方向
用平面 ReadDir + 并发 worker 池遍历；“计数”与“扫描”合并为单趟遍历，扫描进度用计数器累加。
高suggest 联想/纠错词表过滤 O(n²)internal/search/search.go:402,411 · search.go:44
现象
filterTermFragments → containsIn 对全量缓存词表做嵌套循环子串判定；N-gram（2~4）分词使词表规模巨大，每个联想/纠错请求都冷循环一次缓存词表；enumSuggestTerms 虽缓存了词表，但过滤逻辑每次全量执行。
影响
高频搜索联想请求的 CPU 成本随词表规模平方增长。
方向
对候选词建立倒排字典（子串 → 词），或仅对短词做子串映射，把过滤降到接近 O(候选数)。
高监控接口未认证暴露全盘扫描与全表统计router.go:344-349 · internal/monitor/… · monitorservice 路径
现象
/monitor/storage|access|keywords|…|hot-downloads 全部无认证；其中存储统计每次请求对全部根目录 filepath.Walk 做整盘扫描，另有对 operation_records 的 COUNT(*) 全表统计（服务层 :229-250 / :364）。
影响
未授权者可反复触发磁盘 IO 与全表统计，形成廉价 DoS；属“性能 + 安全”双重欠账。
方向
至少添加 AuthRequired + 请求限流；存储统计加带 TTL 的缓存，避免每次请求实时 Walk。
高OpenAPI 每请求 bcrypt + goroutine 写库internal/auth/api_key.go:120 · 中间件“…C”
现象
每次 OpenAPI 调用在 ValidateApiKey 中执行 bcrypt.CompareHashAndPassword（cost 10，约 50–80ms）+ 一次 users/api_keys 查库（先 read 回源），且每请求另起 goroutine 更新 last_used_at（go routine 无界堆积）。
影响
在未开启或不充足限流时，OpenAPI 吞吐被每次 50ms+ 的 bcrypt 串死死扣住；无界 goroutine 冲击内存。
方向
加短 TTL 哈希校验缓存，合并 last_used_at 的异步写（队列化或去抖）。

4. 中风险问题

中上传分片整块读入堆内存internal/services/upload_session.go:207
io.ReadAll(io.LimitReader(req.ChunkData, chunkSize+1)) 将整个分片一次性读入 []byte，再 xxh3 校验 + WriteAt；每片按 chunkSize(默认 10MB) 全量分配并隐性二次拷贝。并发大文件上传时堆内存随请求线性增长，产生 GC 压力。
改为固定 64KB buffer 流式落盘，xxh3 走 io.TeeReader 增量哈希，不再持有整片缓冲。
中每分片独立 GORM 事务（2 UPDATE + 1 INSERT）internal/services/upload_session.go:250-271
每个分片提交一次事务：刷新会话状态、刷新过期时间、插入分片记录。千级分片 = 千次事务，在 SQLite 单写锁下为串行化写热点。
分片记录异步批量/去抖写入，仅在关键节点（finalize、resume）落库，减少写放大。
中哈希写库逐条 UPDATEinternal/index/hashworker.go:325-339
哈希完成批次仍对每个 id 单独 WHERE id=? Updates（最多 500 条独立 UPDATE），仅靠 lockWrite 串行；SQLite 写繁重。
改用 CASE WHEN id … 合并成单条批量 UPDATE，显著降低写放大。
中一致性校验在 Walk 回调内逐条修复internal/index/consistency.go:183,197,252
在遍历回调中直接调用 fixMismatched（单条 UPDATE，未走 lockWrite），背离“先收集后批量”的意图，且可能与扫描写并发竞争。
像 pendingCreate 一样先收集差异，mbatch后再统一批量更新。
中xxh3 小文件整读 + 并行放大internal/pkg/xxh3/xxh3.go:44-50
≤64MB 文件 io.ReadAll 全量读入内存哈希；HashWorker 并发数为 GOMAXPROCS，多个 64MB 同时整读可占数百 MB 堆。
统一 64KB 分块流式哈希，或降低“整读”阈值。
中检索索引重建与增量/查询互斥internal/search/indexer.go:22,66 · search.go:44
RebuildFromDB/ReconcileIndex 与 watcher 增量共用 SearchIndex.mu；重建（如启动全量）期间增量写入与联想查询（读端）都会被阻塞。
内存态原子指针热替换索引，或对重建进行并发隔离。
中SQLite 缺少 synchronous=NORMAL（写满 fsync）internal/appconfig/database.go:206-221
已正确启用 WAL + busy_timeout(2000)，但未设置 synchronous=NORMAL，默认 FULL 下每次提交 fsync；配合默认 8 连接，WAL 下写放大明显。
追加 synchronous(NORMAL)（WAL 下 NORMAL 已提供足够的崩溃安全）；可将 SQLite MaxOpenConns 收敛到 2–4 以降低写锁碰撞。
中审计/记录 worker 逐条落库，缓冲满会阻塞请求internal/services/record_writer.go:35-69 · repositories/upload_repo.go:167
异步队列（4 worker / 256 缓冲）背压合理，但 worker 仍逐条 Create，未批量事务提交；缓冲打满时 Submit 阻塞回退同步，拖慢请求线程。
worker 攒批后单事务批量 insert。
中下载统计与认证回源开销internal/services/download_service.go:65,210,317
每次下载同步执行 attachFileID/IncrementPublicDownloadCount（阻塞 DB 查询），os.Stat 后 http.ServeFile 内部再 stat 一次；认证中间件只缓存“禁用”用户，正常用户每请求仍回源 SELECT disabled WHERE uuid=?。
下载统计关联查询异步化/去抖，去冗余 stat；非禁用态加短 TTL 缓存。

已优化阶段三实施记录（一）suggest 词表倒排化internal/search/search.go · fragment_test.go
倒排过滤
filterTermFragments 先对“更长 ASCII 宿主词”生成 2~4 长度连续子串入 covered 集合，再据此 O(n) 剔除 N-gram 碎片，取代原先对每个 term 全表扫宿主（O(n²)）；新老实现已用等值测试（含随机词表）核对语义一致。
编辑距离剪枝
SuggestCorrectKeywords 先按首字符 + 长度差（|Δlen|≤2）粗筛候选，跳过后注定不能命中（d>2）的 DP 计算；词表频率排序不变。
缓存
过滤后的词表缓存（enumSuggestTerms）只在首次读取或写后节流窗口过后重建，高频键入直接复用，倒排扫描开销由“每次调用”降为“每次失效一次”。
已优化阶段三实施记录（二）检索索引热替换internal/search/indexer.go · search.go
影子重建
RebuildFromDB 在 <dir>.rebuild.<nano> 用独立 writer 全量写盘，全程不触碰线上 writer——重建期间 AutoComplete/SpellCheck/suggest 始终命中旧索引（完整、一致、零写锁阻塞），彻底隔离“重建”与“查询”。
原子切换
新增 rwMu：读方法与增删改持 RLock（读共享），切换在 Lock 下关闭旧 writer → 删除旧目录 → 影子目录提升为规范目录 → 重新打开并重置词表缓存，一份数据集合整体更换，避免中途读到半重建态。
共享化
buildSearchDoc/writeEntries/openBlugeWriter 抽为与实例解耦的函数，线上批量写入与影子重建共用同一套构建逻辑，并用热替换测试（改名/删除/新增、重复重建、缓存放陪后续换）与全量测试套件校验。
已优化阶段三实施记录（三）异步化统计 + 认证回源internal/services/download_count.go · internal/middleware/auth.go
下载计数攒批
下载热路径不再同步 UPDATE 索引表：SubmitDownloadCountIncrement 仅非阻塞入队，后台 worker 周期（2s）或达 256 条映射上限时，用单条 CASE full_path WHEN...END 批量 UPDATE 落库，消除每次下载的写放大与请求线程阻塞（缓冲满仅丢弃计数并告警，背压保护）；关闭时排空落库，并有批量落库测试校验计数正确。
认证回源
用户禁用状态缓存由“仅缓存禁用用户”改为正反两面短 TTL（30s）：命中即免 SELECT disabled，正常用户不再每请求回源；管理员禁用/恢复在 TTL 内生效，记录不存在视为正常并同样入缓存，避免重复查库。
最重要的两项：优先处理文件搜索通配符扫表与监控接口未认证 + 实时整盘扫描——前者决定大库下的查询体验，后者是无需登录即可触发的资源耗尽面。二者均为“性价比最高”的改动点。

8. 方法说明与局限

本次分析方式为静态代码审阅：通过人工 Read 与三路并行子代理分别审查 (1) 文件 I/O / 上传下载存储、(2) 搜索 / 索引 / 扫描 / 哈希、(3) 数据库 / 中间件 / 监控 / 认证 三个簇，并对全部“高”结论做二次 Read 逐条核验行号。部分运行时论断（如 bcrypt 耗时、扫描耗时、内存峰值）为经验估值，未经真实压测校准。

后续建议：基于 /api/v1/health、内置 /api/v1/metrics（Prometheus）与 pprof 补充实测数据；如需，可在正式压测后回填数值。
