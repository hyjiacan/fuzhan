# 系统配置与环境资源要求

> 适用版本：浮栈 (Light Share) v3 | 更新日期：2026-08-27

本文给出在 **启用不同功能** 与 **不同文件规模** 下，对服务器 **CPU / 内存 / 磁盘 / 数据库** 的配置要求与规划建议。

文中涉及的配置项均可在 `fuzhan.yaml`（或配置页）中调整。资源数据为**建议值**，实际占用请以 `/api/v1/metrics`（Prometheus）观测为准。

---

## 1. 总体资源估算模型

进程资源消耗主要由以下几部分构成：

| 资源消费者 | 增长驱动因素 | 主要开销 |
|-----------|------------|---------|
| 文件索引扫描（`index`） | 目录树中的文件/目录总数 | CPU、文件系统 I/O |
| 哈希计算（HashWorker） | 活动**文件总大小**（需读文件内容） | CPU、磁盘读 I/O、内存缓冲 |
| 文件名检索索引（Bluge） | 文件总数 + 文件名平均长度 | 磁盘（索引文件）、查询时内存 |
| SQLite/数据库连接池 | 记录总数 = 文件数 + 条目数 | 内存、磁盘（写锁） |
| 上传分片（`upload.chunk_size`） | 分片并发数 | 内存、磁盘写 I/O |
| 定时清理/一致性校验 | 临时文件、过期会话、全库 | 周期性 CPU/IO |

## 2. 按功能开启的资源要求

启用一项功能前，先确认其资源特征与是否开启的代价一致。

### 2.1 基础服务（默认开启）

| 项 | 建议配置 | 说明 |
|----|---------|------|
| CPU | 1 核 | `server.host`、`server.http.port`；空转占用极低 |
| 内存 | 256MB 起 | Go 运行时 + Gin + 连接池 |
| 磁盘 | 见 §3 | SQLite 默认存于 `<work_dir>/data/fuzhan.db` |

### 2.2 文件索引扫描（`index`，**不可禁用**）

用于将文件系统同步到索引表（`file_records_*`），供列表、搜索、备注、依赖等使用。启动延迟可配，扫描周期用 cron 配置（默认每天 01:00）。

| 项 | 建议配置 | 说明 |
|----|---------|------|
| CPU | 见 §3 | 全量扫描是 CPU + 目录 I/O 密集 |
| 内存 | 200MB 起 | 扫描游标 + 结果缓冲 |
| `index.scan_start_delay_seconds` | 10（默认） | 启动后延迟扫描，避免阻塞就绪 |
| `index.scan_cron_expression` | `0 1 * * *`（默认） | 建议避开业务高峰 |

> 扫描任务会写入任务管理（`task_records`），可在管理页"任务管理"查看进度。

### 2.3 哈希计算（HashWorker）

全量扫描完成后自动触发，计算活动文件的 XXH3 哈希，用于"重复文件"检测。**开销随文件总大小线性增长**。

| 项 | 建议配置 | 说明 |
|----|---------|------|
| CPU | 建议 ≥ 2 核 | 哈希为 CPU + 磁盘读取密集 |
| 磁盘 I/O | 需读一遍所有活动文件内容 | 10G 文件 ≈ 触发 10G 读 I/O |
| 内存 | 256MB 起 | 分帧读取缓冲 |

> 何时开启：仅当需要"重复文件"功能时依赖哈希。超大文件库 + 低配机器，建议错峰扫描（cron 置于低峰），并评估是否接受重复检测的算力成本。

### 2.4 文件名检索索引（Bluge，搜索联想/纠错）

零外部服务的内嵌倒排索引，位于 `<work_dir>/data/search_index`。**启动时全量重建一次，之后增量同步，无定时任务、不写入任务管理。**

| 项 | 建议配置 | 说明 |
|----|---------|------|
| 磁盘 | 每万文件约几十 MB | 与文件名长度相关，远小于文件本体 |
| 内存 | 查询按需加载，常驻开销低 | 连写互斥，读写串行 |
| 启动耗时 | 规模相关，见 §3 | 启动时 `RebuildFromDB` 同步执行 |

> 相关接口：`GET /api/v1/search-suggest`（联想）、`GET /api/v1/search-spellcheck`（纠错）。均为实时查询，单次开销小。

### 2.5 临时文件（`storage.temp`，默认开启）

按 IP 配额的过期分享。后台每 5 分钟清理过期会话与过期文件。

| 项 | 建议配置 | 说明 |
|----|---------|------|
| 磁盘 | ≥ `global` 配额 | `storage.temp.quota.global` 需要足够的落盘空间 |
| 清理 CPU | 低 | 周期清理，随临时文件数上升 |

### 2.6 私有存储（`storage.private`，默认关闭）

需登录、按用户配额。后台每小时清理过期文件。

| 项 | 建议配置 | 说明 |
|----|---------|------|
| 磁盘 | ≥ `global` 配额 | `storage.private.quota.global` |
| 内存 | 低 | 仅启用才常驻 |

### 2.7 WebDAV / FTP / FTPS

网络 I/O 型协议。资源随 **并发连接数** 与 **吞吐** 上升。

| 项 | 建议配置 | 说明 |
|----|---------|------|
| CPU | 每活跃会话建议预留 0.2~0.5 核 | `server.webdav.enabled`、`server.ftp.enabled`、`server.ftps.enabled` |
| 带宽 | 与文件吞吐匹配 | 峰值下载量是主要瓶颈 |
| 内存 | 每连接缓冲 | 大文件流式传输 |

### 2.8 URL 上传（`upload.url_upload.enabled`，默认关闭）

服务端拉取远程文件，占用出网带宽与磁盘。含 SSRF 防护（`allowed_ip_ranges`）。

| 项 | 建议配置 | 说明 |
|----|---------|------|
| 带宽/磁盘 | 与并发拉取量匹配 | 单任务占一份磁盘写 I/O |
| 内存 | 每任务缓冲 | 流式落盘 |

### 2.9 OpenAPI（`open_api.enabled`，默认关闭）

对外 RPC/API，含 IP 白名单 + 频率限制 + 调用统计。

| 项 | 建议配置 | 说明 |
|----|---------|------|
| CPU/内存 | 低 | 受 `rate_limit` 约束，攻击面受 IP 模式下 |
| 调用统计内存 | 定长环形缓冲 | `requests_per_minute` 上限 |

### 2.10 一致性校验（每日 24h 自动）

全库与文件系统逐一比对，开销近似一次全量扫描。自动跳过扫描进行中的时段。

| 项 | 建议配置 | 说明 |
|----|---------|------|
| CPU/IO | 与一次全量扫描相当 | 周期任务，无配置开关 |

## 3. 按文件规模划分的资源建议

以下按 **公开/全部索引文件数** 给出建议基线。目录数与文件数大致同量级。

| 规模 | 文件数 | CPU | 内存 | 数据盘（SQLite+Bluge 索引） | 全量扫描/哈希参考耗时 | 建议数据库 |
|------|--------|-----|------|----------------------------|------------------------|-----------|
| 小型 | ≤ 1 万 | 1 核 | 512MB | 1–5 GB | 秒 ~ 数分钟 | SQLite（默认） |
| 中型 | 1–10 万 | 2 核 | 1–2 GB | 5–20 GB | 分钟级 | SQLite 可承受 /
建议 MySQL |
| 大型 | 10–50 万 | 4 核 | 2–4 GB | 20–100 GB | 10–30 分钟 | MySQL / PostgreSQL |
| 超大型 | 50–100 万 | 8 核 | 4–8 GB | 100–200 GB | 30–60 分钟 | MySQL / PostgreSQL |
| 海量 | > 100 万 | 8+ 核 | 8 GB+ | 200 GB+ | 小时级（建议错峰） | MySQL / PostgreSQL |

**要点：**

- **数据库选型**：≥ 10 万文件强烈建议换 MySQL/PostgreSQL。SQLite 在大记录量 + 全量扫描重写下存在写锁竞争与单次写盘放大，是首要瓶颈。
- **内存中位数**：每 10 万文件额外预留约 0.5–1 GB，覆盖扫描暂存、哈希缓冲、检索引擎分段缓存。
- **磁盘控制项**：`storage.temp`、`storage.private` 的配额决定 Azure 落盘；`upload.max_file_size` 决定单文件峰值写盘。
- **Bluge 检索索引**：与文件数成比例但体量远小于文件本体（每万文件约几十 MB），随文件增删自动维护，无需扩容管理。

---

## 4. 上线前 Checklist

1. 确认文件规模对应 §3 的 CPU/内存/磁盘基线，并按需切到 MySQL/PostgreSQL。
2. 仅在实际需要时开启的耗资源项：
   - 重复文件检测（依赖哈希计算）——大库 + 低配机器需评估。
   - URL 上传 / OpenAPI / WebDAV / FTP——按使用规模开放。
3. 将 `index.scan_cron_expression` 与一致性校验安排在业务低峰。
4. 观察 `/api/v1/metrics`（CPU、内存、文件数、扫描耗时）后回调 §3 建议。

## 5. 相关配置项速查

```yaml
index:
  scan_start_delay_seconds: 10
  scan_cron_expression: "0 1 * * *"

storage:
  temp:
    enabled: true
    quota: { global: 10G, per_ip: 500M }
  private:
    enabled: false
    quota: { global: 100G, per_user: 10G }

upload:
  chunk_size: 10M
  max_file_size: 16G
  url_upload:
    enabled: false

server:
  webdav: { enabled: false }
  ftp:    { enabled: false }
  ftps:   { enabled: false }

preview:
  max_inline_size: 1M
  text_chunk_size: 100K
```

> 更详细的配置语义见 `fuzhan.sample.yaml` 注释与《07-系统配置与选项模块》。
